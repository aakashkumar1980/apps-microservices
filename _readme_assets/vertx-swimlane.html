📊 Vert.x Flow Explanation

Left-to-Right Journey for Each User:

  1. User Layer: 5 users simultaneously send POST requests to port 8080
  2. Boss Thread: Single boss thread accepts connections and distributes to Event Loops
    • Round-robin distribution to 8 Event Loop threads
    • User 1 & 4 → Loop 0 (gets 2 requests)
    • User 2 → Loop 1
    • User 3 → Loop 2
    • User 5 → Loop 3
  3. Event Loop Pool (8 threads): Non-blocking request processing
    • Parse HTTP headers and JSON (very fast: 0.2ms each)
    • Route request to appropriate handler
    • 🟢 Event Loop remains FREE - never blocks!
    • Total Event Loop time: ~0.4ms for Loop 0, ~0.2ms for others
  4. Handler + Callback Registration: Executed ON Event Loop
    • Validate JSON payload
    • Execute business logic (non-blocking parts)
    • Submit blocking DB operation to Worker Thread Pool
    • Register callback function for when DB completes
    • 🟢 Handler returns immediately - doesn't wait!
  5. Worker Thread Pool (20 threads): Handles blocking operations
    • 5 worker threads assigned (one per DB operation)
    • 🔴 Workers BLOCK for 300ms during DB INSERT
    • Critical: Workers block, NOT Event Loops!
    • 15 workers remain available for other blocking tasks
  6. Database Layer: Executes INSERT queries (300ms each)
    • Same execution time as Spring Boot
    • But Event Loops are FREE to handle more requests!
  7. 🔔 Callback Execution: When DB completes (after 300ms)
    • Worker thread triggers the registered callback
    • Callback executes ON the original Event Loop
    • Build JSON response from DB result
    • Send HTTP 200 response to client
    • Worker thread returns to pool
  8. Complete: User receives response after 300ms

✅ The Non-Blocking Advantage

Timeline Analysis - Event Loop vs Worker Thread:

Time Event Loop State Worker Thread State Activity
0-0.5ms ⚡ Active 🟢 Idle Event Loop parsing, routing, registering callback
0.5ms onwards ✅ FREE! ⏳ Waiting Event Loop handles 1000+ more requests!
0.5-300.5ms ✅ FREE 🔴 BLOCKED Worker executes DB operation, Event Loop processes others
300.5-301ms ⚡ Active 🟢 Returning to pool Callback fires on Event Loop, builds & sends response

🎯 Key Architectural Difference

Spring Boot: Request-handling threads (Tomcat pool) do everything including blocking I/O
→ When they block, system cannot accept new requests efficiently

Vert.x: Separation of concerns with two thread pools:

  • Event Loops (8 threads): Handle I/O, never block, always available
  • Worker Pool (20 threads): Handle blocking operations, isolated from request handling

💡 The Magic: Event Loops delegate blocking work to Workers via callbacks, staying free to handle thousands of concurrent connections. This is the reactor pattern in action!
